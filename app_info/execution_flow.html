AgentTPACK: execution flow, object by object

The companion page (architecture.html) explains the modules. This page follows the program instead: each step names the exact class, instance or function that runs, in the order it runs, from building the index to a teacher clicking a citation.

Companion pages: flowchart.html (the whole flow in one picture) · architecture.html (modules and concepts) · all pages

How to read this

Objects are written as module.name, so run.run_pipeline is the function run_pipeline in run.py. Browser code lives in one JavaScript function wrapper in static/index.html, so its functions are written without a module prefix, for example generate(). Two functions share that name: the browser's generate() and the server route api.generate.

class a Python class (type) instance a module-level object created at import function Python function or method browser JavaScript in index.html external library or remote service

The program runs in six phases. T0 happens once, offline. T1 happens each time the server starts. T2 to T6 happen for each lesson.

T0build the index (offline) T1server start-up T2POST /api/generate T3browser renders the plan T4POST /api/materials T5GET /api/chunks/{id} T6print or regenerate

Failure paths

Wherever an AppError is raised, Python unwinds back to FastAPI's exception layer. From there the order is always the same:

raise SomeAppError(message, details) # anywhere in run_pipeline / run_agent / llm / retrieval └─ api.app_error_handler(request, exc) # event: api.error (WARNING if <500, ERROR otherwise) └─ api.error_response(status, code, message, details) └─ JSONResponse {"error": {code, message, details, trace_id}} └─ api.trace_middleware (after call_next) # event: human.response └─ browser readError(res) → applyServerFieldErrors() or showError()

A failure part-way through T2 discards that request's work. For example, if TPACK fails twice, the CK to TPK outputs are lost (they remain in the session log only). Nothing is cached between requests.
