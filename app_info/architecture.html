AgentTPACK: how it works inside

A teacher fills in a browser wizard. The server checks the request, finds the right NCERT Class 7 textbook passages, runs seven Gemini agents and returns a lesson plan with citations to the textbook. A second call then writes the handouts and a quiz. This page follows that path through the code.

Companion pages: flowchart.html (the whole flow in one picture) · execution_flow.html (exact objects, in order) · all pages

Overview

The design is built around the TPACK framework: good technology-supported teaching sits where Content, Pedagogical and Technological knowledge overlap. The code mirrors that literally. Each knowledge area gets its own agent, each overlap of two areas gets its own agent, and a final agent combines everything.

Grounded in the textbook

Agents may only teach what the retrieved passages say. Every phase cites chunk ids, and the frontend resolves each one back to the original paragraph.

Agents in separate domains

CK, PK and TK never see each other's output. The PK and TK prompts forbid stepping into the other domains.

Trade-offs are logged

Every compromise an agent makes (for example "inquiry scoped down because only 11 minutes") is logged and shown to the teacher.

Stateless server

Nothing is stored between calls. The browser holds the plan and sends it back for stage 2.

One request, step by step

Here is what happens between the teacher clicking Generate lesson and the plan appearing. Each step names the log event it writes, so you can match it against python trace.py --last.

  1. Browser builds the payload
    buildPayload() in index.html
    Every wizard input has a data-field such as technology.student_devices. The dotted name becomes the nested JSON path: {content, learners, pedagogy, technology, other_requests}. Empty optional fields are left out. The page sends it with POST /api/generate.
  2. Trace middleware starts a trace
    trace_middleware in api.py → start_trace() · event human.request
    It reuses an incoming X-Trace-Id / X-Request-ID if that is 8–64 safe characters, otherwise makes a new UUID. The id and a per-request seq counter live in contextvars, so every log line from this request is tagged without passing anything around.
  3. Pydantic validates the shape
    TPACKRequest in api.py · event validation.rejected on failure
    Unknown fields are rejected (extra="forbid"). Enums and number ranges are enforced. Every string first goes through sanitize_text() (NFKC normalisation, removing control and zero-width characters, collapsing whitespace), and a blank string becomes None. Failures return 422 with one details[] entry per field.
  4. Route logs the submission and hands off
    generate() in api.py · event human.lesson_submitted
    The route is a plain def, so FastAPI runs it in a thread pool. It calls run.run_pipeline(body).
  5. Safety and consistency checks
    check_safety, check_consistency in validation.py · event validation.passed
    All 8 free-text fields are checked against prompt-injection patterns and then unsafe-content patterns. Contradictory settings (for example a 1:1 device setup with no student devices) raise 422. Softer issues such as "tools listed but no internet" become warnings that are returned with the plan.
  6. Retrieve textbook passages
    retrieve() in retrieval.py · event retrieval.done
    ChromaDB embeds the topic text and returns the 4 closest chunks, filtered to the chosen chapter (where={"chapter_num": N}). Each chunk has an id, text, metadata and a cosine distance.
  7. Relevance gate
    check_relevance in validation.py
    If even the closest chunk is further than RELEVANCE_MAX_DISTANCE = 0.80, the topic is judged not to be in that chapter and the request ends with 422 topic_not_in_source. No LLM call is spent on it.
  8. Seven agents run, one after another
    run_agent() in agents.py · events agent.handoff, agent.start, llm.response, agent.end, agent.decision
    CK → PK → TK → PCK → TCK → TPK → TPACK. Each is one Gemini call. The next section covers who receives what.
  9. Post-processing
    run.py · event citation.invalid when needed
    Citations the model invented are removed, chunk ids that leaked into the prose are scrubbed, the phase timings are checked, content gaps are merged and missing-detail questions are built. See §7.
  10. Response
    event pipeline.done, then human.response
    FastAPI checks the result against GenerateResponse and returns it with an X-Trace-Id header.
  11. Browser renders and immediately asks for stage 2
    renderResult() → loadMaterials()
    The Plan tab appears straight away. The handouts and quiz load in the background with POST /api/materials under the same trace id.

How domain separation is enforced

  • By what each agent is given. run_pipeline builds a separate input dict for each agent. PK is never given the passages and TK is never given the topic, so they cannot leak content.
  • By the prompts. PK must stay "content-free and tool-free", TK must be "descriptive, not prescriptive", TPK must "never state what the topic teaches", and PCK must "never name a tool". Each claim must cite a basis, the request values that justify it.
  • A shared trade-off format. PCK, TCK and TPK each return trade_offs: [{decision, options, chosen, given_up, because}], and TPACK returns design_decisions: [{decision, chosen, rejected, because, agents}].

The trade-off log

After each agent, run._log_decisions(spec, items) writes one agent.decision event per trade-off. The short fields go on the event and the full item goes in detail. It reads:

  • PK's feasibility_notes (requested → alternative, because issue)
  • TK's requested tools whose status is not available
  • PCK / TCK / TPK trade_offs
  • TPACK's design_decisions

python trace.py --decisions prints these per agent. The teacher sees TPACK's decisions under Planning notes → Why the plan looks like this.

How an agent runs

Every agent is a frozen dataclass, defined in agents.py:

AgentSpec(name, prompt_path, required_keys=(), schema=None)

CK    = AgentSpec("ck",  "prompts/ck_agent.md",  ("blocks", "coverage_gaps"))
PCK   = AgentSpec("pck", "prompts/pck_agent.md", ("phase_content_map", "trade_offs"))
TPACK = AgentSpec("tpack", "prompts/tpack_agent.md", schema=LessonPlan)

All prompt files are read into memory once, at import. run_agent(spec, inputs, upstream) then does this:

  1. Log hand-offs. For each upstream agent it writes an agent.handoff event (from, to, payload keys and size). The full payload goes in detail.
  2. Fill the template. Each upstream output is added as {<name>_output}, as pretty-printed JSON. Then prompt.format(**fill) runs. Prompts are Python str.format templates, so literal JSON braces in examples are written {{ }}. A placeholder with no value raises KeyError, which becomes AgentOutputError with reason=prompt_placeholder.
  3. Call the model (event agent.start).
    • Plain agents (CK…TPK): llm.call_agent(), then check that every required_keys entry is present. Missing keys mean a 502 with no retry.
    • Schema agents (TPACK, MATERIALS): _call_with_schema() calls the model and runs schema.model_validate(). If the JSON is invalid or the shape is wrong, it retries once with the validation errors added to the prompt under "Your previous answer was rejected". A second failure raises AgentOutputError (502).
  4. Log the result (event agent.end, with duration, model and token counts). It returns (output, {"agent", "ms", "status"}), which feeds agent_sequence in the response.
The intersection agents' outputs are only checked for the required top-level keys. Their inner shape isn't validated. TPACK and MATERIALS are the only fully schema-validated outputs.

Talking to Gemini

llm.py uses the official openai Python client pointed at https://generativelanguage.googleapis.com/v1beta/openai/. Each call is one user message with temperature=0.3 and response_format={"type": "json_object"}. The client is created lazily, so a missing GEMINI_API_KEY fails a request (502) rather than server start-up. Its built-in retries are off (max_retries=0) so that every retry is logged here.

Retry and fallback

Models are tried in order: GEMINI_MODEL (default gemini-3.6-flash), then each of GEMINI_FALLBACK_MODELS. Each model gets up to 4 attempts, waiting 0 s, 2 s, 6 s and 12 s before them.

What went wrongWhat happens
401 / bad keyFail now: LLMError "rejected the server's credentials"
404 model not foundSkip to the next model at once
Timeout (60 s)Skip to the next model (waiting again rarely helps)
429 rate limitSkip to the next model (quotas are per model)
500 / 502 / 503 / 504 / 529Retry the same model after the next wait
Connection errorRetry the same model after the next wait
Any other 4xxFail now
All models exhaustedllm_exhausted is logged, and the teacher sees a friendly message based on the last reason

Once a reply arrives, the code strips any ``` fences the model added, parses the JSON and requires a JSON object. Otherwise it raises AgentOutputError, which schema agents treat as a reason to retry.

The worst case is slow. 7 sequential calls, each of which can retry and fall back, sit inside one synchronous HTTP request. Expect roughly 1–3 minutes for a plan on a healthy key.

Post-processing the plan

After TPACK returns, run_pipeline cleans up the plan before trusting it:

  1. Remove made-up citations. _strip_invalid_citations keeps only phases[].sources ids that were actually retrieved, and removes duplicates. Anything dropped is counted in notes.removed_references and logged as citation.invalid.
  2. Remove ids from the prose. _scrub_ids_from_text walks the whole plan and deletes chunk-id-looking strings (with brackets or parentheses) from every text field except sources. List items that were only an id are removed.
  3. Check timings. If the phase minutes don't add up to the requested duration, a warning is added (not an error).
  4. Merge content gaps. CK's coverage_gaps and PCK's content_gaps are added to not_covered without duplicates, capped at 20.
  5. Re-validate. The edited plan goes through LessonPlan.model_validate() again, so post-processing can never produce a 500. A failure becomes a 502 with reason=postprocess_invalid.
  6. Build missing-detail questions. PK's and TK's missing_inputs names are normalised and looked up in MISSING_DETAIL_QUESTIONS, which maps each to a wizard field and a plain question. Fields the teacher already filled are skipped (the agent was wrong), and each field is asked about once. Unknown names become a generic question with field: null.

Stage 2: handouts and exit ticket

As soon as the plan is shown, the browser calls POST /api/materials with {request, plan} (the original request plus the plan without missing_details) and the same X-Trace-Id.

  1. Pydantic validates both parts. The plan must be a valid LessonPlan, whose size limits keep the echoed plan small.
  2. run_materials runs check_safety again and repeats retrieval locally (no LLM call). The client might have sent a modified request.
  3. One MATERIALS agent call with upstream={"tpack": plan}, followed by id scrubbing and LessonMaterials validation.

Why a separate call? If Gemini fails here, the teacher still has the plan, and the Handouts and Quiz tabs show a Retry button. LessonMaterials requires every quiz answer to match one of its options exactly and normalises Bloom's labels ("analyse" → "Analyze").

Textbook data pipeline

This runs offline, before the server starts. It turns the raw PDF text of the whole NCERT Science Class 7 book (2018-19 print, 18 chapters) into a searchable vector index.

data/raw/ncert_science_class7.txtraw PDF-to-text dump
→

→
data/chapter01–18.txt## X.Y Title headings, blank-line paragraphs

Chunk ids

g7_ch01_s1.2_000

grade 7 · chapter 01 · section 1.2 · 1st chunk kept in that section. Text before a chapter's first numbered section goes under section X.0 Introduction.

The ids are built only from the chapter number, the section number and the chunk's position in that section, and the collection is deleted and rebuilt on every run. So the same text always gives the same ids, and citations in old logs still resolve. Each chunk's metadata holds grade, chapter_num, chapter, section and source. The chapter_num is what retrieval filters on.

retrieval.py opens the collection lazily on the first request. A missing index returns 503 index_unavailable instead of stopping the server from importing.

Data contracts

lesson_schema.py is shared by the TPACK and MATERIALS prompts (their JSON examples), api.py's response models and the Result screen. Change them together. Extra fields from the model are ignored rather than rejected.

LessonPlan ├─ overview │ ├─ title str ≤200 │ ├─ duration_min int 1–240 │ ├─ objectives[] 1–8 lines │ ├─ materials[] ≤30 │ └─ prep_before_class[] ≤20 ├─ phases[] 1–10 │ ├─ name, minutes (1–180) │ ├─ teacher_steps[] 1–15 # imperative steps │ ├─ student_actions[] ≤15 │ ├─ board_notes str │ ├─ questions[] ≤10 {q, expected_answer} │ ├─ misconceptions[] ≤10 │ ├─ if_tech_missing str # offline fallback │ └─ sources[] ≤10 chunk ids # filtered after the call ├─ not_covered[] ≤20 └─ design_decisions[] ≤12 {decision, chosen, rejected, because[], agents[]} LessonMaterials ├─ handouts[] 1–6 {title, for_phase, instructions, items[1–15]} └─ exit_ticket[] 3–8 └─ {q, type:"mcq", options[2–6, all different], answer ∈ options, why, bloom}

Logging & tracing

Everything goes through one function: log_event(event, actor, level=INFO, detail=None, **fields). It adds trace_id and an increasing seq from the request context and sends the record to three handlers:

HandlerOutputContains detail payloads?
JSON lines (rotating, 5 MB × 5)logs/interactions.jsonlOnly if LOG_FULL_PAYLOADS = True
Consolestderr, one compact line per eventNever
Session file (one per trace)logs/sessions/<YYYYMMDD-HHMMSS>_<trace>.logYes, if LOG_SESSION_PAYLOADS = True (the default)

Rule: large things (agent inputs and outputs, hand-off contents, retrieved passages, prompts) go in detail={…}, never in **fields. The session file is the readable record of one lesson: the plan request, then the materials request and any citation clicks, all under the same trace id.

Key mechanisms

  • Field naming does the wiring. data-field="learners.class_size" sets the JSON path in buildPayload(), the error box id (e-learners.class_size), where server errors land, and the target for "Regenerate with this".
  • Safe rendering. All server and model text goes through the el() helper, which uses textContent. The code never writes server data with innerHTML, so model output can't inject HTML.
  • Citations. sourcesRow() groups a phase's sources by section into "Textbook §1.2" chips. Clicking one fetches GET /api/chunks/{id} for each id, sending the lesson's X-Trace-Id so the click is logged under that lesson, and shows the original passage.
  • Missing details. Each missing_details item is shown with a copy of the matching wizard control. Answering it writes the value back into the wizard and calls generate() again (the full 7-agent run). Answers without a matching field are added to "Anything else".
  • Race guard. loadMaterials() increments state.materialsToken, so a slow stage-2 response for an old lesson is ignored if the teacher has regenerated or started over.
  • Teacher pack. "Download teacher pack" fills #print-pack and calls window.print(). Print-only CSS shows the plan, one page per handout, a student quiz and a separate answer key. There is no server-side PDF. Ctrl+P builds the same pack through beforeprint.

Known gaps

  • Latency. Seven Gemini calls run one after another inside one synchronous request. PCK, TCK and TPK are independent and could run in parallel. The UI still says "usually under a minute".
  • Out-of-date text. The welcome and loading screens and the README still describe 4 agents. The README's troubleshooting snippet uses from llm import client, but the module only has get_client().
  • Trade-offs only partly shown. notes.trade_offs (PCK, TCK, TPK) is returned but not rendered, and design_decisions is not in the printed teacher pack.
  • Loose checks on intersection outputs. PCK, TCK and TPK are checked only for top-level keys. If their inner shape is malformed, it goes straight into the TPACK prompt.
  • Relevance is approximate. Some off-topic queries still pass the threshold (for example "algebra" in chapter 13 at 0.78). CK and PCK content gaps are the second line of defence.
  • Misleading collection name. The collection is called ncert_g7_biology, but it now holds all 18 chapters, including physics and chemistry ones.
  • No auth and no rate limiting. As intended for a proof of concept, so anyone who can reach the server can spend the Gemini quota.
